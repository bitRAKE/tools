Tool Review: rpscan

Date: February 6, 2026

Executive verdict: rpscan is a practical pre-flight safety utility. It overlaps with native commands, but adds a cleaner scanning workflow and consistent output for automation.

What It Does Well

  • Purpose is focused: detect reparse points before destructive file operations.
  • Supports recursive scan, path-only output, and summary stats in one command surface.
  • Skips traversing reparse directories by default, reducing loop risk.
  • Reports tag type and resolved target for common link/junction cases.

Limitations and Risks

  • No built-in policy mode (for example fail if any reparse points are found).
  • No per-tag filtering or richer metadata output.
  • Scope is narrow; it does one thing and depends on users to integrate it correctly.
  • Does not replace ACL, ownership, or broader path-safety auditing.

Alternatives and Tradeoffs

  • PowerShell Get-ChildItem -Attributes ReparsePoint -Recurse: built-in and flexible, but less purpose-shaped output.
  • dir /AL /S and fsutil reparsepoint query: native and available, but fragmented into multiple commands.
  • File explorers / IDEs: easy for one-off checks, weak for reproducible CI/scripting.

rpscan is somewhat replaceable by shell scripting, but still useful as a standardized command in operational runbooks.

Workflow Fit

  • Local development: useful before cleanup scripts and repo-wide deletes/moves.
  • Deployment pipelines: good as a guard step before writing to user-provided paths.
  • Forensics: supports quick discovery of link redirection in suspicious trees.

Evidence Snapshot

  • A fixture with a junction was created and detected: MOUNT_POINT 0xA0000003 ...\j_target -> ...\target.
  • rpscan ... --recursive --paths produced path-only machine-friendly output.
  • rpscan ... --recursive --stats returned concise totals (scanned, reparse).

Final Recommendation

Recommendation: improve. Keep it, then add policy-oriented exit behavior and richer attribute/tag reporting for stronger CI usage.
